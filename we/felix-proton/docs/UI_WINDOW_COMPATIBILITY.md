# Wine窗口问题链与通用解决方案

2026-11-18。Felix Li，使用OpenAI Codex协助。分类：Proton UI兼容性。

本记录承接此前透明黑底、外部透明框、名称/图标和窗口拖动问题。当前案例为直播伴侣；原始桌面、账号配置、厂商程序和运行器二进制留本机。源码及合成测试用于后续继续工作，不表示现有发行版已包含这些候选。

## 可复用结构与启用边界

1. **Wine核心补丁**：0067处理跨进程ARGB，0068修完整目标窗输入计算，0069允许标准标题栏移动，0070修精确装饰角色的全屏状态兼容。源码不硬编码本案例EXE名、标题或屏幕尺寸。
2. **应用profile**：默认保持原行为；沿原图标/入口，在目标应用进程树启用所需能力。0069使用`WINE_X11_NATIVE_MAXIMIZED_MOVE=1`；0070同时要求`WINE_X11_NO_FULLSCREEN_LAYERED_HELPER=1`与精确UTF-8 Win32类名`WINE_X11_NO_FULLSCREEN_HELPER_CLASS`。类名相同不代表角色相同，不能把所有Chromium窗口一律套用。
3. **宿主适配**：RWC外框属于GNOME扩展策略；0070的GTK hint分支只用于Mutter。原生Wine Wayland不经过winex11，KDE等WM需独立验证。当前没有交付跨桌面统一角色识别器。

0070还要求同进程、owned、有captioned顶层owner、LAYERED+TRANSPARENT，并排除APPWINDOW、CHILD、CAPTION、THICKFRAME、MAXIMIZE辅助窗。只补缺失的`_GTK_FRAME_EXTENTS`，保留已有属性，不写主窗、不更改像素/输入。若应用用相同角色承载真实全屏内容，不应启用此声明。

当前通用性证据包括自有不同结构窗口与应用级实机案例：机制可复用、逐应用适配可行；尚未证明所有Wine程序可全局开启。现有自定义alpha开关在Wine/DXVK间还存在`0`关闭语义差异，未来应用策略需支持删除变量与明确继承规则，不能把同一环境变量塞进所有程序。

一手依据：[EWMH窗口移动协议](https://specifications.freedesktop.org/wm/latest/ar01s04.html)、[Mutter50.1整屏兼容分支](https://github.com/GNOME/mutter/blob/50.1/src/x11/window-x11.c#L2690)、[GTK frame元数据解析](https://github.com/GNOME/mutter/blob/50.1/src/x11/window-props.c)。

## 失败尝试与已知边界

- v3/v5只抑制Wine的全屏推断，隔离通过但实机仍被WM置回全屏；v4异步状态同步反向对照未通过；v6样式时序样本未复现旧版反例，未实机安装。均保留历史，不混入最终代码。
- HIDDEN目标、未映射样本、未等WM稳定、无EWMH WM，以及临时runtime副本配额失败不计正向通过；修正条件后的有效结果单列。白块damage/空Bounding试验无效并已恢复。
- 曾因主桌面零显示器导致各版启动失败，亮屏后恢复；不能把这个环境阶段归给单个补丁，也不能把历史PID/窗口ID/token当实时身份。
- 先前还原尺寸每次约增加8×10的现象未单独重测或修复；应用最小宽1080超过1920屏幕半宽960。用户确认两个还原动作正常，不等于几何逐像素一致或厂商尺寸约束已解除。
- 原生Windows、其他WM/原生Wine Wayland、i386 Unix、多屏/混合DPI、长期性能、完整发行构建和跨应用自动启用尚未验收。

## 下一步与回退

后续通用接入应在独立构建目录验证完整匹配队列，先保留默认行为，再给已验证应用增加profile和回退；不要将当前winex11.so直接复制到任意Wine/Proton版本，也不热改使用中的模块。沿原入口加载，保留上游作者、许可证和各自贡献边界。

当前应用级候选按控制器选择和SHA账本回退：先正常停止精确会话，再恢复上一版选择，不删除账号前缀或重写厂商程序。最近v5备份本身仍有全屏误判；更早备份可退0068+0069或0067。回退版本的已知缺陷应保留说明，不能把“可回退”写成旧版也已修复。

公开材料以补丁、测试源、合成输出、技术报告和校验清单组成；真实桌面、认证数据、配置正文、厂商图标及二进制不随本记录上传。当前安装不因文档/源码同步而改变，也不创建新Release。
