# 开播失败、代理与 DNS 排查

## 确认失败发生在哪一步

最初 Ubuntu 客户端在创建直播间时收到 `20054`「开播认证未完成」。带协议确认标记重试后，抖音返回 `4003155`「服务器升级调整中，暂不支持开播」。对应媒体日志尚未开始推流。较早的 `4033059` 来自另一个权限申请请求。两类请求需分别排查。

同一账号在 macOS 也曾出现相同可见提示，Mac 的错误码与出口没有独立核验。用户以前成功用手机开过视频直播。电脑端可另外要求开播资格或认证，错误提示本身无法说明服务正在维护。[抖音开播答疑](https://streamingtool.douyin.com/docs/qna_start_error)

## 区分应用代理、系统 DNS 和实际出口

1. **实际代理路径**。用伴侣网络进程的本地源端口与本机代理连接表对应，确认抖音业务连接曾经走本机 HTTP 代理和日本节点。同链路的无账号出口探测与该地区相符。11:02 的失败重试仍带显式代理参数，该请求的实际出口没有单独取证。
2. **DNS 与 HTTPS 分开验证**。系统解析器能解析 `streamingtool.douyin.com` 与 `webcast3-mate-lq.amemv.com`。绕开代理发起无账号 HTTPS 探测，两域名分别从根路径返回 200 与 404，证明解析及 TLS 可达。Chrome 经显式 HTTP 代理时，由代理侧解析目标域名，所以仅检查系统 DNS 不能代表伴侣走代理时的解析。另有一次在线配置跟踪，约 3.17 秒用在 TLS 握手，该样本只解释启动等待。[Chromium 代理说明](https://chromium.googlesource.com/chromium/src/net/+/cb9cd25315b240a99ac310c14fa9a549c3362939/docs/proxy.md)
3. **应用级直连**。仅在伴侣专属启动流程清理继承的代理环境变量，经官方 Launcher 向 Electron 传入 `--no-proxy-server`。经原图标重开后核对实际进程参数与 TCP 套接字，确认命中两个业务域名的解析结果，经有线网卡发出，采样中没有本机代理连接。系统代理、VPN 设置和宿主路由保持原值。若宿主网络本身通过隧道转发，应用参数只控制 Chromium 的代理选择，出口仍需实测。[Chromium 命令行代理设置](https://www.chromium.org/developers/design-documents/network-settings/)
4. **实际开播**。用户通过这一 Ubuntu 伴侣会话开播成功。媒体 SDK 在 16:13:48 启动 RTMP 推流，16:14:20 停止。应用直连改变了解析路径和出口，单次成功尚无法将历史拒绝单独归因给 DNS 或出口。

复测先看系统解析和直连 HTTPS，再实查伴侣进程的连接。业务 HTTP 响应、直播间创建和媒体推流是不同的检查点。回退时撤下伴侣专属直连设置，在待播状态正常退出后从原图标重开，以恢复之前的选路策略。
